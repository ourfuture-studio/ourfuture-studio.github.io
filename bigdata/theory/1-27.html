배치 처리(Batch Processing)와 스트림 처리(Stream Processing)

끝이 정해진 묶음을 처리하는지, 계속 들어오는 사건을 처리하는지 본다.

관련 문제 풀기조건 바꿔 체험
개념도핵심 수식·판단예제로 이해문제·체험

그림으로 먼저 이해하기

로그가 계속 들어오면 도착 지연도 반드시 0초일까?

이 예제는 끝이 정해진 배치 처리(Batch Processing) 입력과 계속 유입되는 스트림 처리(Stream Processing) 입력을 대비한다. 스트림 처리도 유한한 입력을 다룰 수 있으며, 입력의 범위와 지연 값은 별도로 확인한다.

정식 용어와 정의

배치 처리(Batch Processing)는 일정 범위로 모은 유한 데이터(Bounded Data)를 단위 작업으로 처리하고, 스트림 처리(Stream Processing)는 계속 유입되는 무한 데이터(Unbounded Data)를 지속적으로 처리하는 방식이다. 스트림의 이벤트 시간(Event Time)과 처리 시간(Processing Time)은 다를 수 있으므로 지연 도착·중복·워터마크(Watermark)를 고려하며, 스트림 처리(Stream Processing) 엔진이 유한 데이터(Bounded Data)를 처리할 수도 있다는 점을 구분한다.

전문용어와 정의 출처 펼쳐 보기
  • 배치 처리(Batch Processing)
  • 스트림 처리(Stream Processing)
  • 유한 데이터(Bounded Data)
  • 무한 데이터(Unbounded Data)
  • 이벤트 시간(Event Time)
  • 처리 시간(Processing Time)
  • 워터마크(Watermark)
  • 지연시간(Latency)

정의 참고: Apache Beam — Basics of the Beam model, Bounded vs. unbounded; timestamps; watermarks

핵심 이론

하루가 끝난 주문 파일을 모아 다음 날 처리하는 것은 배치 처리(Batch Processing)의 예다. 계속 발생하는 로그를 받아 짧은 간격으로 이상 징후를 갱신하는 것은 스트림 처리(Stream Processing)의 예다. 저장 장치 이름보다 입력이 끝나는 묶음인지 계속 늘어나는 흐름인지가 직접적인 구분이다.

스트림을 사용한다고 지연이 정확히 0이 되는 것은 아니다. 네트워크 전송, 대기, 집계(Aggregation) 간격과 처리 시간(Processing Time)이 있다. 사건이 실제 발생한 시각과 시스템에 도착해 처리된 시각도 다를 수 있으므로 “실시간”이라는 표현만으로 모든 도착 순서를 보장하지 않는다.

늦게 도착한 로그를 어느 집계(Aggregation) 구간에 포함할지, 중복 수집을 어떻게 다룰지도 설계 조건이다. Apache Beam은 범위가 정해진 bounded 자료와 계속 늘어나는 unbounded 자료를 구분한다. bounded 자료도 스트리밍 엔진에서 처리할 수 있으므로 입력의 끝이 있다는 사실과 실행 방식 자체를 같은 정의로 보지는 않는다. 여기서는 하루 확정 파일을 한 번 처리하는 예와 끝없이 유입되는 로그를 계속 처리하는 예를 함께 정해 비교한다.

핵심 수식

이 사건의 도착 지연

Δt=ta−te

긴 수식은 좌우로 넘겨 전체 식을 볼 수 있습니다.

Δt
도착 지연(Arrival Delay)
t_a
도착 시각
t_e
사건 발생 시각(Event Time)

10:00:05 − 10:00:00 = 5초다.

적용 조건: 같은 시계 기준으로 기록된 한 사건의 두 시각을 비교하는 자체 예다. 전체 처리 성능을 측정한 값은 아니다.

정의와 원리 참고: Apache Beam: Basics of the Beam model

작은 예제로 확인하기

기존 오류 X는 10:00:00에 발생해 10:00:05에 도착했다. 입력은 계속 증가한다.

  1. 1입력 범위 읽기

    끝이 정해지지 않고 계속 증가하므로 스트림 예다.

  2. 2두 시각의 차이 계산

    도착 시각에서 발생 시각을 빼면 5초다.

기본은 스트림 처리의 예이지만 도착 지연은 5초다.

이 예제의 유한·계속 유입 대비를 모든 배치·스트림의 일대일 분류 규칙으로 일반화하지 않는다. 한 사건의 도착 지연도 전체 파이프라인 응답 시간이나 최대 지연이 아니다.

기존 예제의 조건과 표 자세히 보기

자체 로그에서 두 시각을 나눈다.

사건 발생 도착·처리
오류 X 10:00:00 10:00:05

차이는 5초다. 계속 수집하는 방식이어도 실제 지연이 있을 수 있다. 이 수치는 실제 서버 측정 결과가 아니다. 10:00:00 발생 로그가 10:00:05에 도착한 사례의 차이는 5초다. 이 값은 입력 한 건의 도착 지연일 뿐 전체 파이프라인(Pipeline) 응답 시간이나 모든 로그의 최대 지연이 아니다. 하루 파일을 다음 날 처리하는 방식은 입력 묶음의 끝이 정해져 있다는 점에서 다르며 “파일이므로 무조건 느리다”는 결론도 나오지 않는다.

정답과 오답의 이유 확인하기

정답 2번 — 스트림 처리(Stream Processing)이며 지연은 별도 확인

계속 늘어나는 입력을 처리하는 스트림이며 실제 지연과 순서는 별도의 조건이다.

  • 1번은 정해진 묶음을 모으는 방식이다.
  • 3번은 전송·처리 지연을 무시한다.
  • 4번은 늦은 도착 가능성을 없다고 단정한다.
