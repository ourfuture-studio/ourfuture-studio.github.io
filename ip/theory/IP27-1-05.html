애자일의 반복에 피드백 넣기

관련 문제 1개조건 바꿔 체험

작은 기간마다 무엇을 전달하고 무엇을 고치는지 살펴본다.

핵심 이론

반복은 개발 활동을 여러 주기로 수행하는 것이다. 애자일 원칙은 동작하는 소프트웨어의 잦은 전달, 요구 변화의 수용, 팀의 정기적 성찰을 함께 제시한다.

2주마다 일정을 끝냈더라도 결과를 사용해 보거나 요구·작업 방식을 조정하지 않으면 피드백을 반영한 반복인지 확인할 수 없다.

애자일이 문서나 계획의 부재를 뜻하지는 않는다. 이 예제에서는 반복의 길이가 아니라 전달물과 피드백에 따른 변경 기록을 비교한다.

작은 예제로 확인하기

팀은 2주마다 실행 가능한 기능을 사용자에게 보여 준다. 이번 시연에서 '검색 결과에서 신청으로 바로 이동' 요구를 받아 다음 주기 작업 우선순위를 바꾸고 회고에서 검토 방식을 수정했다.

조건 판단과 결과
2주 주기; 실행 기능 시연; 사용자 검색→신청 이동 요구 수집; 다음 주기 우선순위 조정; 회고로 검토 방식 변경. 피드백 반영 기록 있음
2주 주기; 실행 기능 시연; 동일한 사용자 요구 수집; 다음 주기 계획과 검토 방식을 변경하지 않고 판단 이유도 기록하지 않음. 주기만으로 피드백 반영 확인 불가
3주 주기; 실행 기능 시연; 검색→신청 이동 요구 수집; 다음 주기 우선순위 조정; 회고로 검토 방식 변경. 피드백 반영 기록 있음

기간은 반복의 틀이다. 사용자 요구가 다음 주기의 우선순위를 바꾸고 회고가 검토 방식을 바꾼 기록이 피드백 반영의 직접 근거다.
