개발 단계마다 보안 근거 남기기

관련 문제 1개조건 바꿔 체험

최종 검사에 앞서 요구와 설계에서 통제할 위험을 정한다.

핵심 이론

Secure SDLC는 개발 생명주기에 보안 활동을 통합하는 접근이다. SSDF는 보안 요구·설계 위험·구현 검토·검증·취약점 대응을 연결한다.

설계에서 권한 경계를 정하지 않았다면 완성 후 스캔만으로 업무상 권한 규칙이 저절로 만들어지지 않는다.

보안 검토가 일찍 있었더라도 이후 검증이 면제되지는 않는다. 위험·설계 결정·검증 사례 사이의 연결을 유지한다.

작은 예제로 확인하기

프로젝트는 문서 편집 권한 위험을 다룬다. 보안 계획에 요구 단계의 작성자 규칙, 설계 단계의 서버 권한 검사, 구현 단계의 검토, 시험 단계의 타인 문서 편집 거부 사례를 연결해야 한다.

조건 판단과 결과
위험=타인 문서 편집; 요구 작성자만·설계 서버 검사·구현 검토·시험 타인 거부를 모두 연결 기록. 명시한 활동 연결 충족
위험=타인 문서 편집; 최종 포트 스캔만 수행; 업무 권한 요구/설계/거부 테스트 기록 없음. 업무 권한 검증 연결 미확인
위험=타인 문서 편집; 요구 작성자만·설계 서버 검사·구현 검토 연결; 타인 거부 실행 테스트는 미수행. 시험 결과 미확인

요구에서 정한 작성자 규칙이 설계·코드·시험에 각각 어떻게 반영됐는지 연결해야 한다. 같은 위험을 다루는 네 활동을 추적할 수 있게 남긴다.

다시 떠올릴 단서

보안 요구가 어느 설계·코드·검증으로 이어졌는지 추적한다.

적용 범위

자체 추적 예제이며 SSDF 전체 준수 인증이나 취약점 부재 증명이 아니다.
