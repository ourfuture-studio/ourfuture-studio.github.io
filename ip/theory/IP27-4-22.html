컨테이너와 VM이 공유하는 커널의 범위

관련 문제 1개조건 바꿔 체험

격리된 실행 환경이라는 말만으로 각 환경이 별도 커널을 가진다고 생각하면 안 된다.

핵심 이론

일반 Linux 컨테이너는 실행 호스트의 커널을 공유하면서 프로세스·파일 시스템 등의 실행 환경을 구분한다. 애플리케이션과 필요한 파일을 묶지만 컨테이너마다 별도 게스트 커널을 부팅하는 방식은 아니다.

가상머신은 가상 하드웨어 위에 각 게스트 운영체제와 그 커널을 실행할 수 있다. 같은 물리 호스트의 두 VM이라도 응용이 직접 사용하는 게스트 커널은 서로 다른 인스턴스다.

컨테이너가 Linux VM 안에서 돌면 그 VM의 게스트 커널을 공유한다. 이때 물리 호스트 OS의 커널을 직접 공유한다고 바꾸어 말하면 층을 혼동한다. 커널 공유 여부만으로 모든 보안 경계의 강도·성능 우열을 정하지 않으며 특수 런타임은 별도 조건이다.

작은 예제로 확인하기

물리 서버의 Linux 호스트 커널은K다. 별도 VM 없이 일반 Linux 프로세스 컨테이너C1·C2를 같은 호스트에서 실행하고 응용A·B를 각각 넣었다.

배치 응용A의 커널 응용B의 커널
같은 Linux 호스트의 컨테이너2개 K K
서로 다른 VM2개 G1 G2
한 Linux VM 안의 컨테이너2개 G1 G1

같은 호스트의 일반 Linux 컨테이너 두 개는 사용자 공간을 구분하면서 같은 커널K를 사용한다.

다시 떠올릴 단서

응용이 직접 사용하는 커널이 호스트 커널인지 게스트 커널인지 배치 층을 따라간다.

적용 범위

일반 Linux 컨테이너·VM 배치에 따른 커널 공유 범위의 교육 모형이다. 실제 VM·컨테이너 배포·탈출 공격·보안성·성능 측정을 수행하지 않았다.
