모듈 사이 정보와 결합도

관련 문제 2개조건 바꿔 체험

다른 모듈의 내부에 얼마나 의존하는지 비교한다.

핵심 이론

결합도(coupling)는 모듈 사이의 상호 의존 정도다. 공개 인터페이스와 내부 저장 구조를 구분하면 어떤 변경이 상대 모듈에 전파되는지 볼 수 있다.

합계 계산에 단가와 수량만 필요하다면 두 값을 전달하는 계약과 주문 전체의 내부 필드 배치에 의존하는 계약은 변경 영향이 다르다.

인수가 적다는 사실만으로 항상 결합도가 낮다고 판정하지 않는다. 전역 상태나 내부 필드의 직접 수정 여부도 조건에 포함한다.

결합도의 이름과 순서

이 글의 전통적 여섯 등급은 약한 쪽부터 자료 → 스탬프 → 제어 → 외부 → 공통 → 내용 순으로 읽는다. 필요한 값만 주고받는지, 상대의 실행을 제어하는지, 전역 상태나 내부 구현을 함께 사용하는지를 확인한다.

등급: 약→강 English 의존 방식 작은 예
자료 Data Coupling 필요한 개별 값을 인자로 전달 total(unitPrice, quantity)
스탬프 Stamp Coupling 복합 자료를 전달하고 일부 구성만 이용 주문 객체 전체를 받고 금액 필드만 읽기
제어 Control Coupling 다른 모듈의 처리 선택을 제어하는 정보 전달 작업 종류 플래그 전달
외부 External Coupling 외부 규약·형식·장치에 함께 의존 같은 외부 통신 형식 준수
공통 Common Coupling 전역 자료를 함께 사용 전역 주문 객체 공동 수정
내용 Content Coupling 다른 모듈의 내부 코드·자료에 직접 의존 상대 모듈 내부 저장 위치 직접 수정

기억 순서는 “자·스·제·외·공·내”다. 자료 구조를 전달한다는 사실만 보지 말고 실제로 쓰는 정보와 변경 의존성을 함께 확인한다.

작은 예제로 확인하기

함수 total은 정수 단가와 수량만 필요하고 결과는 단가×수량이다. 다른 모듈의 주소·고객정보는 필요 없다. 비교 목표는 주문 객체 내부 구조에 대한 의존을 줄이는 것이다.

조건 판단과 결과
total의 정의=단가×수량; 단가=7, 수량=3; 호출은 total(7, 3); 주문의 주소 필드만 개명한다. 결과 21, 호출 계약 유지
total=단가×수량; 주문 내부 필드 price=7,qty=3을 직접 읽는다. price 필드 이름만 unitPrice로 바꾸고 total은 수정하지 않는다. 기존 필드 참조 계약 불일치
total=단가×수량; 공개 호출 total(7, 3)을 total(8, 3)으로 바꾸며 구조는 동일하다. 결과 24, 입력 계약 유지

계산에 필요한 값은 단가와 수량뿐이다. 이 값만 명시한 인터페이스는 주소·고객정보나 내부 배치 변경의 영향을 줄인다.
