모듈 안의 책임과 응집도

관련 문제 2개조건 바꿔 체험

함께 둔 코드가 어떤 한 목적을 수행하는지 살펴본다.

핵심 이론

모듈은 경계와 인터페이스를 가진 코드 단위다. 응집도(cohesion)는 그 안의 요소가 서로 얼마나 관련되는지 보는 기준이다.

청구서 금액 계산에 필요한 세금·할인 계산을 한 책임으로 묶은 경우와, 단지 아침에 실행한다는 이유로 백업·메일·금액 계산을 묶은 경우는 묶는 근거가 다르다.

같은 파일에 있다고 응집도가 높아지는 것은 아니다. 아래 등급 이름과 순서를 익히면서 각 함수가 공통 목적에 필요한지도 검토한다.

응집도의 이름과 순서

이 글에서는 전통적인 일곱 등급을 강한 쪽부터 기능적 → 순차적 → 교환적 → 절차적 → 시간적 → 논리적 → 우연적 순으로 비교한다. 등급명과 함께 “무엇이 요소들을 묶는가?”를 읽는다. 같은 날 실행한다는 이유만으로 백업·메일·금액 계산을 묶은 예는 시간적 응집도이고, 청구 금액 하나를 만들기 위해 세금·할인을 계산하는 예는 기능적 응집도다.

등급: 강→약 English 요소를 묶는 기준 작은 예
기능적 Functional Cohesion 한 기능을 완성하는 데 필요한 요소 청구 금액 계산
순차적 Sequential Cohesion 앞 단계의 출력이 다음 단계의 입력 입력 읽기 → 그 결과 검증
교환적·통신적 Communicational Cohesion 같은 입력·출력 자료를 사용 같은 주문으로 영수증과 배송장 작성
절차적 Procedural Cohesion 공통 자료보다 실행 순서로 연결 서로 다른 자료를 다루는 점검을 정해진 순서로 실행
시간적 Temporal Cohesion 실행 시점이 같음 시작 시 수행하는 초기화 묶음
논리적 Logical Cohesion 비슷한 종류의 기능 중 하나를 선택 종류 플래그로 여러 입력 처리 중 하나 선택
우연적 Coincidental Cohesion 공통 목적·자료·순서가 없음 관련 없는 보조 기능 모음

기억 순서는 “기·순·교·절·시·논·우”다. 이것은 설계 의존성을 설명하는 분류이며, 등급 이름 하나가 모든 프로그램의 설계 품질을 수치로 확정하지는 않는다.

작은 예제로 확인하기

모듈 M은 청구서 합계를 만드는 책임만 가진다. 함수는 상품 합계, 세금 계산, 할인 적용이다. 후보 함수 중 M의 책임과 직접 관련 없는 하나를 찾는다.

조건 판단과 결과
M 책임=청구서 합계; 포함 후보=상품 합계·세금·할인·프로필 사진 크기 조정. 사진 조정은 분리 후보
M 책임=청구서 합계; 상품 합계·세금·할인에 최종 금액 반올림 추가. 같은 책임으로 설명 가능
M 책임을 '아침 실행 작업'으로 이름 붙이고 백업·날씨 메일·청구서 계산을 함께 둔다. 시간만 공통인 묶음

M의 목적은 금액 산출이다. 반올림·상품 합산·세금 합산은 이 출력에 기여하지만 프로필 사진 조정은 다른 변경 이유와 출력을 가진다.
