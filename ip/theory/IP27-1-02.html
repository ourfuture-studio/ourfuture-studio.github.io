구조와 메시지 순서를 구분하는 UML

관련 문제 1개조건 바꿔 체험

같은 주문 시스템도 관계를 묻는지 호출 순서를 묻는지에 따라 표현이 달라진다.

핵심 이론

UML은 시스템을 여러 관점에서 기술하는 모델링 언어다. 클래스 다이어그램은 클래스의 속성·연산·관계 같은 구조를, 순서 다이어그램은 참여자 사이 메시지의 순서를 표현한다.

주문이 결제 객체를 참조한다는 관계만으로 결제 요청이 재고 확인보다 먼저 일어나는지는 알 수 없다. 호출 순서를 보려면 상호작용을 별도로 명시한다.

순서 다이어그램의 위아래 배치는 사건의 선후를 표현하지만, 별도 시간 제약이 없으면 줄 사이 간격을 밀리초로 읽지 않는다.

작은 예제로 확인하기

주문·재고·결제라는 클래스와 참조 관계는 그대로 둔다. 변경 전 메시지는 '재고 확인→결제 요청', 변경 후는 '결제 요청→재고 확인'이다. 구체 메시지 선후 변경을 기록하려 한다.

조건 판단과 결과
클래스는 주문·재고·결제, 참조 관계 동일. 재고 확인→결제 요청을 결제 요청→재고 확인으로 바꾼다. 순서 다이어그램의 메시지 순서 변경
클래스는 주문·재고·결제, 기존 메시지 선후는 동일. 주문에 배송주소 속성만 추가한다. 클래스 다이어그램의 주문 속성 변경
클래스는 주문·재고·결제·쿠폰, 기존 메시지 선후 동일. 주문과 쿠폰 사이 참조 관계만 추가한다. 클래스 다이어그램의 관계 변경

변경 전후 클래스와 관계는 같고 메시지 순서만 다르다. 구조도만으로 차이를 표현할 수 없으므로 순서 다이어그램에서 두 메시지의 선후를 바꾼다.

다시 떠올릴 단서

구조는 클래스 관점, 메시지 선후는 상호작용 관점에서 본다.

적용 범위

한 다이어그램이 시스템 전체를 증명하지 않는다. 코드 자동 생성이나 실행 시간 추정은 다루지 않는다.
