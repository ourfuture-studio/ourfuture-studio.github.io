잠금의 대기 방향으로 교착 찾기

관련 문제 1개조건 바꿔 체험

잠금은 충돌을 기다리게 할 수 있지만 두 거래가 서로 기다리는 순환도 만들 수 있다.

핵심 이론

배타 잠금은 같은 객체에 대해 다른 거래의 충돌하는 접근을 허용하지 않는다. 이 예제에서는 배타 잠금을 얻어야만 작업하며 커밋·중단 때까지 보유하는 작은 모형을 사용한다.

대기 그래프에서 T1→T2는 T1이 T2가 가진 잠금을 기다린다는 뜻이다. T1→T2→T1의 순환이 생기면 어느 쪽도 스스로 다음 잠금을 얻을 수 없어 교착상태가 된다.

PostgreSQL은 교착을 탐지해 관련 거래 하나를 중단할 수 있으며 어느 거래가 선택될지는 단정하지 않는다. 여러 객체의 잠금 순서를 모든 거래에서 같게 정하면 이 두 객체의 반대 순서 교착을 피할 수 있다. 이것만으로 모든 동시성 문제를 해결한 것은 아니다.

작은 예제로 확인하기

배타 잠금만 있는 교육 모형이다. A·B는 서로 다른 객체이며 각 거래는 커밋까지 잠금을 유지한다. 순서 T1 lock A, T2 lock B, T1 request B, T2 request A이고 아직 커밋·중단·타임아웃·교착 탐지는 수행되지 않았다.

순서 동작
1 T1이 A 배타 잠금 획득
2 T2가 B 배타 잠금 획득
3 T1이 B 요청 →T2 대기
4 T2가 A 요청 →T1 대기

대기 방향이 T1→T2와 T2→T1으로 이어져 순환한다. 잠금 사용 자체가 교착을 방지하지 않는다.

다시 떠올릴 단서

누가 누구의 잠금을 기다리는지 간선을 그려 순환 여부를 검사한다.

적용 범위

정의한 배타 잠금·대기 그래프 모형을 계산한다. PostgreSQL 잠금 모드 전체나 실제 교착 탐지·희생 거래 선택을 실행한 실험이 아니다.
