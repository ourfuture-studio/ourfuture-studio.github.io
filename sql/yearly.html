ROLLUP·CUBE: 그룹 조합과 결과 행은 다릅니다

집계(Aggregation)의 종류가 몇 개인지와 실제로 몇 행이 나오는지는 따로 셉니다.

판단 기준

ROLLUP(a,b)는 (a,b) → (a) → () 순서의 그룹화 집합(Grouping Set)을 만듭니다. CUBE(a,b)는 여기에 (b)도 포함합니다. 각 집합 안에 실제로 존재하는 그룹 수를 더해야 결과 행 수가 됩니다.

짧은 자체 예시로 확인하기

직접 만든 매출(Sales) 자료입니다. 채널(channel)·품목(item)은 NULL이 없고 각 행은 별도 거래입니다. 총매출은 25입니다.

channelitemamount
온라인컵14
매장컵6
온라인병5

조건을 적용하면

집계 방법그룹화 집합실제 결과 행 수
ROLLUP(channel,item)(channel,item), (channel), ()3 + 2 + 1 = 6
CUBE(channel,item)(channel,item), (channel), (item), ()3 + 2 + 2 + 1 = 8

상세 조합은 3개, 채널은 2개, 품목은 2개입니다. 빈 괄호 ()는 전체를 하나로 묶는 총계(Grand Total)입니다. CUBE는 품목만 묶은 컵 20·병 5의 두 행을 추가합니다.

Oracle 19c의 ROLLUP·CUBE 정의를 작은 자료에 적용한 예시입니다. 총계 표시의 NULL과 원래 값의 NULL은 GROUPING으로 구분합니다. 표시 순서는 ORDER BY를 별도로 지정해야 합니다.

기억할 한 줄 조합을 먼저 펼친 뒤, 각 조합에서 생기는 그룹을 셉니다. 2ⁿ은 CUBE의 조합 수입니다.

ERD: 최대 수·필수 참여·식별 관계를 따로 읽으세요

관계선 하나에서 모든 조건을 추측하지 말고, 양쪽에서 한 개체가 몇 개와 연결되는지 읽습니다.

판단 기준

엔터티 관계 다이어그램(ERD, Entity-Relationship Diagram)의 카디널리티(Cardinality)는 연결 가능한 수를, 선택·필수 참여(Optional / Mandatory Participation)는 0개가 가능한지를 나타냅니다. 식별 관계(Identifying Relationship)는 부모 식별자가 자식 식별자에 포함되는지로 구별합니다.

짧은 자체 예시로 확인하기

새로 만든 자전거 대여소 모형입니다. 아래 숫자 범례에서 Station (1) — (0..N) Bike는 “자전거 한 대는 대여소 한 곳, 대여소 한 곳은 자전거 0대 이상”을 뜻합니다.

읽을 항목명시한 조건뜻
Bike 쪽 0..NStation 한 곳에 Bike 0대 이상빈 대여소도 허용
Station 쪽 1Bike 한 대에 Station 정확히 한 곳자전거는 대여소 없이 존재할 수 없음
외래 키(Foreign Key)Bike.station_id: NOT NULL + FKNULL과 없는 대여소 번호를 막음
기본 키(Primary Key)Bike의 PK는 bike_id 하나station_id가 자식 PK에 없으므로 이 설계는 비식별 관계

조건을 적용하면

데이터 상황허용 여부판단 근거
S1에 자전거 B11·B12가 있음허용대여소 하나에 여러 자전거 가능
S2에 자전거가 없음허용Bike 쪽 최소 수가 0
B13의 station_id가 NULL불가NOT NULL 위반
B14가 존재하지 않는 S9를 참조불가외래 키 위반

자전거 쪽 참조가 필수라는 조건은 모든 대여소에 자전거가 있다는 뜻이 아닙니다. 외래 키가 있다는 사실과 부모 키가 자식 기본 키에 포함된다는 사실도 구분합니다.

숫자 범례와 키·제약을 명시한 자체 모형입니다. ERD 표기법에 따라 선·화살표·기호의 모양은 달라집니다. 범례 없이 특정 선 모양에 보편적인 의미를 부여하지 않습니다.

기억할 한 줄 “대여소 한 곳에 자전거가 몇 대인가?”와 “자전거 한 대에 대여소가 몇 곳인가?”를 각각 묻습니다.

NULL: 평균의 분모와 대체 시점을 확인하세요

NULL을 0으로 바꾸는 위치가 같아 보여도 집계(Aggregation)의 결과는 달라질 수 있습니다.

판단 기준

AVG(qty)는 NULL이 아닌 qty만 평균에 포함합니다. AVG(COALESCE(qty,0))는 계산 전에 NULL을 0으로 바꾸므로 그 행도 분모에 들어갑니다. COALESCE(AVG(qty),0)는 평균 계산이 끝난 뒤 결과가 NULL일 때만 0으로 바꿉니다.

짧은 자체 예시로 확인하기

서로 다른 배송 묶음(Delivery Batch) 3개에서 qty를 기록했습니다. 세 번째 값은 0이 아니라 알 수 없는 값인 NULL입니다.

batch_idqty
20118
2026
203NULL

표현식(Expression)계산 과정결과

긴 SQL: 중간에 남는 행부터 확인하세요

SQL 문장이 길어질수록 최종 숫자를 바로 암산하지 말고, 각 단계에서 남는 행과 중복을 표시합니다.

판단 기준

서브쿼리(Subquery)가 어떤 행을 만드는지 확인하고, 조인(Join)이 만드는 행 쌍을 센 뒤 집계(Aggregation)를 적용합니다. LEFT JOIN에서 매칭되지 않은 회원은 NULL로 보완한 한 행이 남으므로 COUNT(*)와 COUNT(오른쪽 열)는 다를 수 있습니다.

짧은 자체 예시로 확인하기

새로 만든 회원(Member)·대여(Rental) 자료입니다. 회원은 A·B·C 세 명이고 대여가 진행 중(ACTIVE)인 횟수를 회원별로 셉니다.

WITH members(member_id) AS (
  SELECT 'A' UNION ALL SELECT 'B' UNION ALL SELECT 'C'
), rentals(rental_id, member_id, status) AS (
  SELECT 71, 'A', 'ACTIVE' UNION ALL
  SELECT 72, 'A', 'ACTIVE' UNION ALL
  SELECT 73, 'B', 'RETURNED'
)
SELECT m.member_id, COUNT(a.member_id) AS active_count
FROM members m
LEFT JOIN (SELECT member_id FROM rentals WHERE status = 'ACTIVE') a
  ON a.member_id = m.member_id
GROUP BY m.member_id
ORDER BY m.member_id;

서브쿼리는 71·72번만 남깁니다. A는 두 대여 행과 연결되고 B·C는 NULL 보완 행이 하나씩 생깁니다. 오른쪽 member_id를 세면 B·C는 0이며 COUNT(*)로 바꾸면 각각 1이 됩니다.

중간 표는 이해를 위한 논리적 분해(Logical Decomposition)입니다. DBMS가 이 순서대로 물리 실행한다는 뜻은 아닙니다. 아래 자체 SQL은 SQLite로 실행 대조했으며 결과 순서는 ORDER BY로 지정했습니다.

행·열 전환(PIVOT/UNPIVOT)은 남는 열과 NULL부터

PIVOT은 집계한 값을 열로 펼칩니다. UNPIVOT은 열을 행으로 펼치지만, 집계 전에 있던 개별 행을 되살리는 연산은 아닙니다.

판단 기준

PIVOT의 집계 함수(Aggregate Function)와 전환 기준에 쓰이지 않은 입력 열이 암묵적 그룹화(Implicit Grouping)의 기준이 됩니다. UNPIVOT은 NULL인 값을 기본적으로 제외하며 INCLUDE NULLS를 지정하면 포함합니다.

짧은 자체 예시로 확인하기

직접 만든 팀별 분기 실적입니다. 입력은 team·term·amount 세 열뿐이며, Oracle 19c의 SUM(amount) PIVOT으로 Q1·Q2를 열로 펼칩니다.

예시 SQL 보기
-- Oracle Database 19c
WITH src (team, term, amount) AS (
  SELECT 'Alpha', 'Q1', 14 FROM dual UNION ALL
  SELECT 'Alpha', 'Q1', 6 FROM dual UNION ALL
  SELECT 'Alpha', 'Q2', 9 FROM dual UNION ALL
  SELECT 'Beta', 'Q1', 4 FROM dual UNION ALL
  SELECT 'Beta', 'Q2', CAST(NULL AS NUMBER) FROM dual
)
SELECT team, q1, q2
FROM src
PIVOT (SUM(amount) FOR term IN ('Q1' AS q1, 'Q2' AS q2))
ORDER BY team;

집계·전환에 쓰이지 않은 team만 그룹 기준으로 남습니다. Alpha의 Q1 두 행은 20으로 합쳐집니다. 이 결과를 기본 UNPIVOT하면 NULL인 Beta·Q2는 빠져 3행이며, INCLUDE NULLS이면 4행입니다. 어느 쪽도 원래 5행을 복구하지 않습니다.

아래 SQL은 Oracle 19c 문법입니다. 연결한 실험은 GROUP BY의 기초 비교이며 PIVOT 실행기가 아닙니다. 집계 전 입력에 별도 식별 열을 남기면 그룹이 더 나뉠 수 있습니다.

정규표현식(Regular Expression)은 패턴과 몇 번째 일치를 나눠 읽기

함수 이름만 외우면 숫자 한 글자와 숫자 묶음, 검색 시작 위치와 일치 횟수를 혼동하기 쉽습니다.

판단 기준

[0-9]는 숫자 한 글자, [0-9]+는 연속된 숫자 한 개 이상을 뜻합니다. REGEXP_SUBSTR의 position은 1부터 세는 검색 시작 문자 위치, occurrence는 그 위치부터 찾은 몇 번째 일치(Match)를 반환할지 정합니다.

짧은 자체 예시로 확인하기

자체 상품 코드에서 연속된 숫자 묶음을 찾습니다. 두 호출 모두 position=1이며 occurrence만 1과 2로 바꿉니다.

상품 코드(code_text)
BOX
KIT-26-804
PACK-5

조건을 적용하면

code_text첫 번째 일치두 번째 일치
BOXNULLNULL
KIT-26-80426804
PACK-55NULL
예시 SQL 보기
-- Oracle Database 19c
WITH src (code_text) AS (
  SELECT 'KIT-26-804' FROM dual UNION ALL
  SELECT 'PACK-5' FROM dual UNION ALL
  SELECT 'BOX' FROM dual
)
SELECT code_text,
       REGEXP_SUBSTR(code_text, '[0-9]+', 1, 1) AS first_match,
       REGEXP_SUBSTR(code_text, '[0-9]+', 1, 2) AS second_match
FROM src
ORDER BY code_text;

KIT-26-804에서 [0-9]+가 찾는 묶음은 26과 804입니다. occurrence=2는 두 번째 문자부터 찾으라는 뜻이 아닙니다. 필요한 순번의 일치가 없으면 Oracle REGEXP_SUBSTR는 NULL을 반환합니다.

ASCII 숫자를 다룬 Oracle 19c 예시입니다. 연결한 자료는 반환값 NULL의 기초 확인이며 정규표현식 전용 문제·실행기는 아닙니다.

기억할 한 줄 문자 클래스(Character Class) → 수량자(Quantifier) → 검색 시작 위치(Position) → 몇 번째 일치(Occurrence) 순서로 확인합니다.

문자열 함수(String Function): 지울 문자와 방향을 먼저

TRIM 계열 함수는 문자열 양끝을 정리합니다. 문자열 중간의 글자를 모두 찾아 지우거나, 정해진 단어 전체를 교체하는 함수와 구분합니다.

판단 기준

Oracle TRIM은 기본적으로 양끝의 공백을 제거하고, 지정한 방향(LEADING/TRAILING/BOTH)과 제거할 한 문자를 적용할 수 있습니다. LTRIM·RTRIM의 두 번째 인자는 제거할 문자 집합(Character Set)이며 정확히 일치해야 하는 단어가 아닙니다.

짧은 자체 예시로 확인하기

자체 문자열 A='..pear..', B='ababaZab'를 비교합니다. 작은따옴표는 SQL 문자열 리터럴(String Literal)의 경계이며 실제 값에 포함되지 않습니다.

이름문자열
A..pear..
BababaZab

조건을 적용하면

Oracle 호출반환 문자열
TRIM(A)..pear..
TRIM(BOTH '.' FROM A)pear
LTRIM(B, 'ab')Zab
RTRIM(B, 'ab')ababaZ
예시 SQL 보기
-- Oracle Database 19c
SELECT TRIM('..pear..') AS default_trim,
       TRIM(BOTH '.' FROM '..pear..') AS dot_trim,
       LTRIM('ababaZab', 'ab') AS left_trim,
       RTRIM('ababaZab', 'ab') AS right_trim
FROM dual;

기본 TRIM은 점을 지우지 않습니다. 점을 지정하면 양끝 점이 없어집니다. LTRIM은 a와 b가 반복되어도 왼쪽에서 계속 제거하다가 Z에서 멈추며, RTRIM은 오른쪽에서 같은 규칙을 적용합니다.

Oracle 19c 문법을 기준으로 한 예시입니다. DBMS에 따라 TRIM의 인자 문법이 다릅니다. 연결한 자료는 빈 문자열·공백·NULL의 기초 비교입니다.

윈도우 함수(Window Function): 순위·구간·프레임을 구분하기

RANK·DENSE_RANK는 동점의 순위를, NTILE은 정렬된 행을 나눈 구간 번호를 계산합니다. 같은 정렬값이 같은 구간에 들어간다고 가정하면 안 됩니다.

판단 기준

RANK는 동점 뒤 순위를 건너뛰며 DENSE_RANK는 건너뛰지 않습니다. NTILE(n)은 정렬된 행들을 크기 차이가 최대 1인 구간(Bucket)으로 나누고, 남는 행은 앞 구간부터 배분합니다. 각 OVER 절의 정렬 기준을 따로 읽습니다. 윈도우 프레임(Window Frame)은 누적 합계 등의 계산에 포함할 행 범위입니다.

짧은 자체 예시로 확인하기

자체 점수표입니다. 두 순위 함수는 points DESC만 사용해 동점을 유지하고, NTILE(3)은 points DESC, player_id ASC로 행 순서를 확정합니다.

예시 SQL 보기
-- Oracle Database 19c
WITH scores (player_id, points) AS (
  SELECT 'K01', 96 FROM dual UNION ALL
  SELECT 'K02', 88 FROM dual UNION ALL
  SELECT 'K03', 88 FROM dual UNION ALL
  SELECT 'K04', 72 FROM dual UNION ALL
  SELECT 'K05', 64 FROM dual
)
SELECT player_id, points,
       RANK() OVER (ORDER BY points DESC) AS rnk,
       DENSE_RANK() OVER (ORDER BY points DESC) AS dense_rnk,
       NTILE(3) OVER (ORDER BY points DESC, player_id ASC) AS bucket
FROM scores
ORDER BY points DESC, player_id ASC;

88점 두 행 다음의 RANK는 4, DENSE_RANK는 3입니다. NTILE(3)은 5행을 2·2·1행으로 나누므로 같은 88점도 다른 구간에 배정됩니다. 누적 합계에서 ROWS·RANGE가 포함하는 행은 아래 프레임 이론으로 이어서 비교합니다.

player_id는 유일합니다. 순위 함수의 OVER 절에 player_id까지 넣으면 88점 두 행도 서로 다른 정렬값이 되어 동점 순위가 바뀝니다. FLOOR의 음수 예시는 원문 시험 문항의 재현이 아닙니다.

기억할 한 줄 순위(Rank), 구간(Bucket), 윈도우 프레임(Window Frame)은 서로 다른 질문입니다. FLOOR는 별도의 수치 함수(Numeric Function)로, FLOOR(-2.4)=-3입니다.

정렬(Ordering)을 끝낸 뒤 몇 번째 행인지 판단하기

입력표에서 세 번째였던 행이 정렬 후에도 세 번째인 것은 아닙니다. DESC는 바로 앞 정렬 표현식에 적용됩니다.

판단 기준

ORDER BY는 왼쪽 정렬 키(Sort Key)부터 적용합니다. 첫 키가 같을 때만 다음 키를 비교합니다. 모든 정렬 키가 같은 행들의 상대 순서는 확정되지 않습니다. 특정 순번을 확정하는 예시에서는 전체 정렬 키의 조합이 행을 유일하게 구분하도록 조건을 명시합니다. 이 예시는 유일한 order_id를 마지막 키로 사용합니다.

짧은 자체 예시로 확인하기

자체 배차 요청표를 urgency DESC, wait_minutes ASC, order_id ASC로 정렬합니다. order_id는 유일하며 모든 값은 NULL이 아닌 정수입니다.

예시 SQL 보기
-- Oracle Database 19c
WITH dispatch (order_id, urgency, wait_minutes) AS (
  SELECT 71, 2, 20 FROM dual UNION ALL
  SELECT 74, 2, 10 FROM dual UNION ALL
  SELECT 72, 1, 15 FROM dual UNION ALL
  SELECT 73, 2, 10 FROM dual
)
SELECT order_id, urgency, wait_minutes
FROM dispatch
ORDER BY urgency DESC, wait_minutes ASC, order_id ASC;

긴급도2를 먼저 모으고, 그 안에서 대기시간10인 두 행을 앞으로 보냅니다. 두 행의 마지막 동점은 order_id ASC로 풀어 73,74가 됩니다. 따라서 세 번째 출력 행은71입니다.

ORDER BY가 없으면 출력 순서를 보장할 수 없습니다. NULL의 기본 정렬 위치는 DBMS별로 확인해야 하며, 이 예시는 그 차이를 섞지 않도록 NULL을 사용하지 않았습니다.

정규화(Normalization): 키 이름보다 함수 종속을 보세요

표에 중복이 보인다는 이유만으로 정규형(Normal Form)을 단정하지 않습니다. 먼저 업무 규칙으로 키와 함수 종속을 명시합니다.

판단 기준

제2정규형(2NF, Second Normal Form)은 1NF를 만족하면서 모든 비주요 속성(Non-prime Attribute)이 각 후보 키(Candidate Key) 전체에 완전 함수 종속되는지 봅니다. 제3정규형(3NF, Third Normal Form)은 비자명한(Nontrivial) X → A마다 X가 슈퍼 키(Superkey)이거나 A가 주요 속성(Prime Attribute)인지 확인합니다.

짧은 자체 예시로 확인하기

자체 배송 명세(Shipment Line)입니다. 후보 키는 (delivery_id,item_code) 하나라고 정합니다. 업무 규칙은 delivery_id → depot_code, depot_code → depot_phone, (delivery_id,item_code) → qty입니다. 표본 몇 행에서 추측한 규칙이 아닙니다.

delivery_iditem_codedepot_codedepot_phoneqty
S7BK1D202-51002
S7BK2D202-51001
S8BK1D302-62003

조건을 적용하면

분해한 관계(Relation)키(Key)남긴 함수 종속(Functional Dependency)
Shipment(delivery_id,depot_code)delivery_iddelivery_id → depot_code
Depot(depot_code,depot_phone)depot_codedepot_code → depot_phone
ShipmentLine(delivery_id,item_code,qty)(delivery_id,item_code)(delivery_id,item_code) → qty

depot_code·depot_phone은 복합 키의 일부인 delivery_id만으로 결정되므로 원래 표는 2NF가 아닙니다. delivery_id → depot_code → depot_phone의 이행적 함수 종속(Transitive Functional Dependency)도 나누었습니다. 위 세 관계는 주어진 종속 아래에서 원래 자료를 손실 없이 연결할 수 있습니다.

1NF를 만족하고 위에 명시한 종속만 주어진 작은 예시입니다. 실제 설계에서는 모든 후보 키·업무 규칙·무손실 분해(Lossless Decomposition)를 확인해야 합니다. 새 일련번호를 붙이는 것만으로 원래 종속이 사라지지는 않습니다.

기억할 한 줄 어느 속성이 어느 속성을 결정하는지 화살표로 그린 뒤, 키 일부에 대한 종속과 비키 결정자의 종속을 찾습니다.
