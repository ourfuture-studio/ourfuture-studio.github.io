이 주제 직접 체험하기

GitHub SQL 실험실은 SQLite로 실행됩니다. Oracle 전용 코드는 Oracle 체험에서 실행합니다.

핵심 먼저 이 예제에서는 수량·단가를 업무 입력, 주문 번호를 설계를 위해 부여한 식별 값, 금액을 수량×단가로 계산한 값으로 정합니다. 기본·설계·파생 속성의 분류는 이름이나 자료형만으로 결정되지 않습니다.

어떤 자료와 조건을 볼까요

할인·세금·반올림이 없는 작은 주문 자료입니다. 금액을 계산할 수도 있고 계산 결과를 따로 저장할 수도 있습니다. 둘을 모두 저장했을 때 불일치가 생기는지 확인합니다.

답을 가르는 기준은 무엇일까요

파생 값은 다른 속성으로부터 정해진 규칙으로 구할 수 있습니다. 저장 여부와 파생 여부는 별개의 판단입니다. 저장된 금액도 계산 근거가 있다면 파생 값일 수 있습니다.

실제 업무에서 결제 확정 금액이 별도 사실이라면 현재 단가×수량과 같아야 한다고 단정할 수 없습니다. 이 글의 일치 조건은 할인 등이 없다고 정한 예제에 한정합니다.

Oracle에서 첫 조건을 확인해 봅니다

실행 1 · 저장 값과 계산 값

복사한 쿼리를 Oracle 체험(FreeSQL)에 붙여 넣어 실행하세요.

WITH order_lines (order_id, qty, unit_price, saved_total) AS (
    SELECT 101, 2, 3000, 6000 FROM dual
    UNION ALL
    SELECT 102, 1, 2000, 2000 FROM dual
)
SELECT order_id, qty, unit_price, saved_total,
 qty * unit_price AS calculated_total
FROM order_lines ORDER BY order_id;

예상 결과

ORDER_ID QTY UNIT_PRICE SAVED_TOTAL CALCULATED_TOTAL
101 2 3000 6000 6000
102 1 2000 2000 2000

조건과 구조를 바꾸어 비교해 봅니다

실행 2 · 한 값만 바뀌면

복사한 쿼리를 Oracle 체험(FreeSQL)에 붙여 넣어 실행하세요.

WITH order_lines (order_id, qty, unit_price, saved_total) AS (
    SELECT 101, 2, 3000, 5000 FROM dual
    UNION ALL
    SELECT 102, 1, 2000, 2000 FROM dual
)
SELECT order_id, saved_total, qty * unit_price AS calculated_total
FROM order_lines WHERE saved_total <> qty * unit_price
ORDER BY order_id;

예상 결과

ORDER_ID SAVED_TOTAL CALCULATED_TOTAL
101 5000 6000

두 번째 조회는 정한 계산 규칙과 다른 101번만 찾습니다. 이 SQL이 기본·설계·파생이라는 분류 자체를 증명하는 것은 아닙니다. 분류 근거는 앞서 정한 업무 생성 방식입니다.

결과를 어디까지 해석할 수 있을까요

주문 번호도 실제 업무에서 이미 부여받는 번호라면 단순히 번호라는 이유로 설계 속성이라고 할 수 없습니다. 같은 이름이라도 업무 정의를 먼저 확인합니다.
