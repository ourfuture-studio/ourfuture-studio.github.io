01 · 표를 나누는 이유를 눈으로 보기

정규화 (Normalization)

교수 이름이 바뀌었는데 수강 기록마다 다르게 고쳐졌다면? 어떤 사실을 어디에 한 번 저장할지 정하는 과정입니다. 아래 단계와 작업을 바꾸어 표·연결선·수정 위치를 비교하세요.

이 예제에서 정한 업무 규칙
  • 한 학생은 같은 과목을 한 번 수강합니다. 수강의 기본 키(PK, Primary Key)는 (student_id, course_id)입니다.
  • 학생ID가 학생명을, 과목ID가 과목명·담당 교수ID를, 교수ID가 교수명을 결정합니다. 이 함수 종속(FD, Functional Dependency)은 업무 규칙으로 가정한 것이며, 네 행만 보고 추측한 규칙이 아닙니다.
  • 한 과목에 담당 교수가 여러 명이거나 재수강 이력을 관리한다면 키와 관계부터 다시 설계해야 합니다.

나눈 표를 조인하면 원래 수강 정보가 돌아올까요?

기본 자료에서는 키를 기준으로 조인하면 같은 수강 네 행을 복원합니다. 무손실 분해(Lossless Decomposition)는 표를 아무렇게나 잘라도 된다는 뜻이 아닙니다. 여기서는 공통 속성이 분리한 한쪽 관계의 키인 조건을 이용했습니다. 별도로 추가한 교수·수강하지 않는 학생은 내부 조인한 수강 결과에 새 행을 만들지 않습니다.

SELECT e.student_id, e.course_id, s.student_name,
       c.course_name, c.prof_id, p.prof_name
FROM Enrollments e
JOIN Students s   ON s.student_id = e.student_id
JOIN Courses c    ON c.course_id = e.course_id
JOIN Professors p ON p.prof_id = c.prof_id;

위 SQL은 3NF 설계의 재결합 예시입니다. 이 그림의 자료 계산은 화면 안의 교육용 모형이며, Oracle에서 실행·검증했다는 표시가 아닙니다.

제1정규형 (1NF, First Normal Form)

이 모형에서 한 칸에 수강 과목 목록을 넣지 않고, 하나의 속성값을 저장합니다. 1NF가 되었다고 중복된 학생명·교수명이나 모든 이상 현상이 사라지는 것은 아닙니다.

제2정규형 (2NF, Second Normal Form)

1NF를 만족하고, 모든 비주요 속성(Non-prime Attribute)이 어떤 후보 키(Candidate Key)의 진부분집합에도 부분 함수 종속(Partial Functional Dependency)하지 않아야 합니다. 이 예제의 후보 키는 학생ID와 과목ID의 조합 하나입니다.

제3정규형 (3NF, Third Normal Form)

모든 비자명 함수 종속(Non-trivial Functional Dependency) X → A에서 X가 슈퍼 키(Superkey)이거나 A가 주요 속성(Prime Attribute)이어야 합니다. 이 예제에서는 과목ID → 교수ID → 교수명의 이행 함수 종속(Transitive Functional Dependency)을 분리합니다.

정규화는 표의 수를 무조건 늘리거나 속도가 반드시 빨라지는 기법이 아닙니다. 업무 규칙과 종속성을 보존하며 중복·이상 현상을 줄이는 설계 과정입니다. 보이스-코드 정규형(BCNF, Boyce–Codd Normal Form)은 모든 비자명 종속의 결정자가 슈퍼 키여야 하는 더 강한 조건이며, 3NF와 같은 정의가 아닙니다.

여기서 헷갈리기 쉬운 점

  • GROUP BY와 PARTITION BY는 출력 순서를 보장하지 않습니다. 예제 SQL의 마지막 ORDER BY가 표시 순서를 정합니다.
  • 이 분석 함수의 OVER 안에는 ORDER BY가 없으므로 파티션 전체를 계산합니다. 누적 합계(Running Total)와 같은 예제가 아닙니다.
  • PARTITION BY가 보존하는 것은 분석 함수 단계에 들어온 행입니다. 같은 조회에 WHERE·GROUP BY·HAVING이 있다면 그 처리가 끝난 행을 대상으로 계산합니다. 여기서 분석 함수 조회에는 WHERE·GROUP BY·HAVING을 추가하지 않았으며, 두 조회는 같은 원본을 각각 사용합니다.
  • NULL인 그룹 키끼리도 하나의 그룹·파티션에 속합니다. 이것이 NULL = NULL 비교가 TRUE라는 뜻은 아닙니다. COUNT(*)는 모든 행을, COUNT(amount)는 NULL이 아닌 금액을 셉니다. SUM·AVG는 NULL을 제외하며, 금액이 전부 NULL인 그룹은 결과도 NULL입니다.
  • 빈 표에 GROUP BY customer를 적용하면 그룹이 없어 0행입니다. GROUP BY 없이 표 전체에 적용하는 단일 집계는 결과 행 수가 다를 수 있습니다.

04 · 행을 거를까, 그룹을 거를까?

WHERE · HAVING (Row Filtering · Group Filtering)

WHERE는 집계 전 개별 행을, HAVING은 만들어진 그룹을 제한합니다. “주문 한 건의 금액”과 “고객별 주문 합계”를 구분하고, 사라진 행이 어디에서 빠졌는지 따라가세요.

같은 숫자 50으로 비교해 보세요

아래 같은 기준 50으로 비교를 누르면 WHERE만 적용됩니다. 고객 A의 10원 주문이 빠져 합계는 100이 됩니다. 모드를 HAVING만으로 바꾸면 A의 합계는 110, 고객 C의 합계50도 남아 결과는 2행 → 3행이 됩니다.

조건에 따른 행과 그룹을 준비하고 있습니다.

현재 그림에 대응하는 SQL

예제는 GROUP BY customer가 있는 조회입니다. ORDER BY customer NULLS LAST를 명시해 출력 순서를 정했습니다. GROUP BY 자체가 정렬을 보장하지 않습니다.

WHERE에서 이미 빠졌다면?

WHERE amount >= 50은 각 주문을 판단합니다. A의 10원 주문을 제외하면 뒤의 SUM(amount)에도 들어가지 않습니다. HAVING이 그 주문을 다시 불러오지는 않습니다.

HAVING에서 빠지는 것은?

HAVING SUM(amount) >= 100은 집계한 고객 그룹을 판단합니다. 조건을 만족하지 않는 고객의 결과 행 전체가 제외됩니다. 원본 테이블의 주문을 삭제하는 작업은 아닙니다.

항상 서로 바꿀 수 있을까요?

집계함수(Aggregate Function)의 조건은 같은 조회 수준의 WHERE에 둘 수 없습니다. 그룹 기준 열의 조건은 경우에 따라 동등하게 옮길 수 있지만, 개별 금액 조건과 합계 조건은 서로 다른 질문입니다. HAVING은 GROUP BY 없이 전체 자료를 하나의 그룹으로 집계하는 조회에도 사용할 수 있습니다.

이 그림은 의미를 이해하기 위한 논리적 처리 순서이며, 데이터베이스 옵티마이저(Query Optimizer)의 실제 물리적 실행 순서를 그대로 보여주는 실행 계획(Execution Plan)은 아닙니다. 그림 자료를 JavaScript로 계산하며, 새 Oracle 실행 결과라고 표시하지 않습니다.
